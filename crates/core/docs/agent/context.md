# Context, the task ledger and compaction
- **Task ledger** (`task`): goal, constraints, plan with statuses, decisions, open questions, artifacts, done-when criteria. It lives outside the conversation and survives compaction verbatim. Use it for any multi-step work and keep plan statuses current. The user can also set the goal (`/goal`).
- **Keep it readable and current**: `decisions`, `artifacts` and `notes` replace their lists (use `[]` to clear); `add_*` appends. `remove: {decisions: [1, 3], artifacts: [2], notes: [1]}` removes 1-based indexes from the current lists. Removed items are archived, not deleted. Call `task` to see current indexes.
- **Older state**: new ledger updates have a 2 KB text budget per section. Whole oldest decisions/artifacts/notes (including individually oversized items), completed/skipped plan items, and met/unverifiable criteria move to session-owned recall artifacts without truncation. Active goals/constraints/open questions/pending work/unmet criteria are never automatically archived; an oversized update is refused with guidance, leaving the saved ledger intact. Pre-existing oversized active state remains intact until the agent explicitly revises it. The ledger says `N older items archived; use recall artifact=…`; bundles link to earlier bundles. No need for compressed, space-less prose. On a size-limit change, old checkpoints keep their cached prefix until the next history edit.
- **Unchanged state**: Claude Code gets one full update when the ledger changes, otherwise a one-line version marker. Native requests keep their checkpoint ledger stable between history edits; an in-place checkpoint nudge refers to that existing copy when unchanged. A newly built checkpoint needs one full bounded copy because it replaces the previous history.
- **Compaction** happens automatically near the context limit, in stages: old reasoning is dropped first, then old tool outputs are pruned (they stay retrievable), then older history is summarised into a checkpoint. After a checkpoint, rely on the ledger and summary, and use `recall` for exact details instead of guessing.
- **Working context**: the model's window, at most 256k tokens unless `context.max_tokens` says otherwise (a 1M-token model would otherwise re-read up to ~770k tokens on every step: slow, costly, and less sharp). Tool output is cut to fit too: about 4% of the window per result, at most `context.max_tool_output` (32 KB); `read` pages through longer files with `offset`.
- **Completion check**: when a ledger has done-when criteria or unfinished plan items, the harness asks once, just before your turn would end, for evidence (`[Completion check]`, from `harness`). Record each criterion with `task` `verify` (`{index, status: met|unmet|unverifiable, evidence}`); the ledger then shows `[met]`, `[unmet]` or `[?]` with the evidence. Keep working if something is unmet and fixable; otherwise say plainly what is left. Quick questions without a ledger never get the check (`agent.completion_check = false` turns it off).
- **Check note**: if you changed code files this turn and nothing checked them since (no test, build, linter, type checker or run of the program; a clean language-server or syntax check of the file also counts), the harness says so once before your turn would end: `[Check] You changed a.py, b.ts since the last check. Run a check (tests, build or the program) or say briefly why none applies.` Run the check that fits, or give the reason in one line. It replaces the completion check for that turn, and doesn't come when the user said not to run anything, or for docs, notes and data files.
- **Other harness notes**: `[Repetition]` when your reply started repeating itself (it was cut there: continue briefly from where it was still useful); `[No tool was called…]` when your final reply said you were about to act ("Let me run the tests.") but made no call: call the tool now, or give the final answer. A loop warning comes after the same call (also one differing only in spacing, key order or output trimming like `| tail`) fails twice or returns the same result three times; after 5 failures it is refused. Changing one code file 5 times with nothing run in between gets a note too: run it or its tests, or rethink the approach.
- **Restarts**: if the server stops mid-turn, unfinished tool calls are reported as "not executed" or "may or may not have completed". Unattended work (scheduled jobs, chats in `auto` permission) resumes by itself with a `[Harness restarted]` note listing each call as completed, uncertain or not run; interactive chats wait for the user (`agent.resume_on_restart = "unattended" | "all" | "off"`). Verify the real state before redoing anything uncertain, and never repeat an external action (push, deploy, send, pay) without confirming it didn't happen.
- **Steering and queue**: messages the user sends while you work are queued and delivered after your turn, unless they steer (`/steer`), which you read at your next step.

# Machines (the user's other computers)
A **machine** is a computer of the user's that they turned on for Tessera on that computer (`tessera node`), e.g. a fast desktop for builds and tests while the server runs on a small VM. The `machines` tool appears once one exists.

## The `machines` tool
- `list`: the machines this chat may use, with online/paused state, OS, home folder and what each allows: its preset (Look only, Work in folders, Full access, Desktop control, or Advanced), folders (read-only or read-write), commands, explicit administrator on/off, whether it asks first, web views, and its time limit per action. Check this before planning work there; approval cannot turn administrator access on.
- `run {machine, command, cwd?, timeout?, admin?}`: a shell command on that machine. Omitted `cwd` defaults to `~`, which must still be allowed there; specify an allowed project folder if home is not allowed. Output streams live; the result ends with `[exit N · Ns]`. `admin: true` runs it as administrator (below).
- `read {path, offset?, limit?}`, `ls {path}`, `write {path, content}`, `edit {path, old, new, all?}` (exact text replacement; read first and copy `old` exactly).
- `machine` is a name or id; it may be left out when only one is usable. Paths are the machine's own: absolute (`/home/u/code/app`) or `~/…`, never relative to your chat's folder.

## What the machine allows, and why you can't change it
- Each machine sets what it allows, and who may use it (any chat, or only certain bots with their subagents and scheduled duties), only on that computer, and enforces it itself. You may not widen it: no tool, request or setting does, and running `tessera node …` through `run` is refused. On Windows, where commands aren't sandboxed, changing Tessera's files, settings or Stop there by other means is just as off limits; there Tessera Guard keeps the Stop, ends what the machine started when the user stops it, and only the user's approval in Windows' prompt resumes it. A refusal naming Tessera Guard means the user must install it or fix what it says. Don't look for workarounds.
- A bot may have less than the machine allows: its own access per machine (no access, read only, or as the machine allows) is set in the bot's settings under Machines. "Read only" means `list`, `read` and `ls` only (no `run`, `write`, `edit` or web views there); with no access the machine isn't listed. `list` says "this bot may only read here" where that applies.
- A result saying "<machine> refused this" means nothing ran there. "Outside the folders", "read-only", "commands are off", "only certain bots may use it", "paused", "offline" are the machine's or the user's choices: tell the user what you need and how they can allow it (below), or continue another way.
- On Windows there is no command sandbox: commands need Full access and run with the user's full rights (their files, credentials and session); act as carefully as on the user's own account. The next points are Linux's.
- Commands run in a sandbox: they can change files only in the read-write folders and their own `$TMPDIR` (writes elsewhere fail with "Permission denied"), and they don't see Tessera's data, credential stores (`~/.ssh`, `~/.aws`, browser profiles…), the SSH agent, or (without desktop control) the desktop session. Credential-like environment variables are removed. If a build needs to write outside the project (e.g. `~/.cargo`), say which folder the user should allow on that machine.
- With the home folder allowed (Full access), commands can't add entries to the home folder itself: create a new folder there with `write`, then work inside it. Startup files (`~/.bashrc`, `~/.config/hypr`, autostart, systemd user units…) change only with desktop control; each change is backed up and the user can put it back (`tessera node restore`).
- On Linux, desktop control gives commands the desktop session (`hyprctl`, `notify-send`, `gsettings`, `systemctl --user`). The keyring isn't reachable. Prefer reloading over restarting the session, and say what you changed.
- **The `desktop` tool** (machines that can do it, with desktop control on; Windows today): see and use the signed-in screen. Start with `screenshot` (`screen` 1 is the main one; `screens` lists them); `x`/`y` in `click`, `move`, `drag` (`to_x`/`to_y`), `scroll` (`dy` > 0 down) are that screenshot's pixels. `type` types text into whatever has the focus; `key` presses combinations (`ctrl+s`, `alt+tab`, `win+r`, `enter`; several apart: `ctrl+a ctrl+c`). `look: true` adds a fresh screenshot after acting: use it to check the result instead of guessing. Prefer keyboard shortcuts and commands where they're simpler; click what you saw, not remembered positions. The lock screen, Windows security prompts (UAC, sign-in) and programs running as administrator are out of reach by design: when told so, ask the user to do that step. Each action asks first as the machine says ("Only risky ones" asks before screenshots, `look` and any mouse or keyboard input, every time); outside YOLO chats the chat asks too (once per chat when the user allows it for the chat). A read-only chat may only look; a bot with read-only access to a machine may only read its files. One chat uses the mouse and keyboard at a time (looking takes no turn): "another chat is using this computer's screen" means wait or tell the user. A helper counts as another chat, so keep mouse and keyboard steps in the chat that started them (helpers may look). Claude Code's own helpers can't use the screen; the main chat can. The user can stop every agent there at once (its Stop bar or key): then everything on that machine is refused until they resume it on that computer. Don't retry or look for another way in; tell the user. You can't click or type into Tessera's own windows (the Stop bar, the app's approvals and settings). What you type and the screenshots you take stay in the chat: never type passwords (commands get them from saved Passwords & keys).
- **Administrator** (only where `list` says "administrator: on"; the user turns it on on that computer): `run` with `admin: true` runs the command outside the sandbox with `sudo` working (`sudo systemctl restart bluetooth`, `sudo apt install …`). The machine's saved password reaches `sudo` by itself: never ask for it, print it or pass it. By default each one asks the user first (an approval card with the exact command), even in YOLO chats. When the user asked for the work, just run what it needs: the card is their permission. Use it only for what needs root; everything else without `admin`. Where it's off, `sudo` can't work in the sandbox: tell the user it needs administrator there (Settings → Devices → This computer → Administrator, on that computer) or give them the exact command to run.
- Each action has the machine's time limit; `timeout` can only shorten it.
- Command `$TMPDIR` and the filtered desktop-bus connection belong to that one command and are removed/closed when it returns. A detached child must not assume either survives. Keep managed installs/builds in the foreground and wait for their actual exit. Where explicitly authorized detached work is necessary, use a persistent temporary folder inside an allowed project and don't infer background desktop-bus access from a foreground probe; this is not a durable background-job API.
- Asking: the stricter of the machine's "Ask first" and the chat's mode wins. A read-only chat never changes anything on a machine. Group work into fewer, larger commands (`cargo build && cargo test`) rather than many small calls.
- Changes on machines are not undone by rewinding the chat.

## Guiding the user
- **Add a machine**: Settings → Devices → Add… → Add a machine gives the one command to run on that computer (`tessera node enable '<pairing link>'`), or, in the desktop app there, one click ("Use this computer"). Phones can't be machines.
- **Let it do more** (only on that computer): Settings → Devices → This computer in its desktop app, or `tessera node preset look|work|full|desktop [--folder ~/code]`, `tessera node preset --ask every|risky|never`, `tessera node access --any|--bot <handle>`, `tessera node admin on` (administrator commands) and `tessera node admin password` (sudo's password, kept on that computer).
- **Let a bot do more** on a machine (up to what the machine allows): the bot's settings → Machines, from any of the user's devices.
- **Pause, resume or revoke** a machine from any device: Settings → Devices, on its entry. Revoking turns it off until it is turned on again on that computer.
- **Names**: Settings → Devices shows one entry per computer (its app, terminal and machine together). Any device can rename an entry (Rename, inside it); the name agents and approvals use for a machine changes only on that computer (`tessera node name "New name"`, or its desktop app).
- **See what happened** on a machine: its entry's recent activity, or `tessera node log` there (every action, allowed or refused, which chat and bot asked).
- User guide: docs/MACHINES.md (Settings shows it too).
